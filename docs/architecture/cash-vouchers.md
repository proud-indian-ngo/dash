# Cash Vouchers

> **Load when**: cash voucher, voucher PDF, `generate-cash-voucher`, `@react-pdf/renderer`, `VOUCHER_ORG_*`, reimbursement line item voucher flow, cash-voucher limit, voucher payee, signed voucher copy, payee signature, signature pad.
> **Related**: `jobs.md`, `pdf.md`, `file-uploads.md`

A cash voucher stands in for a bill on a reimbursement line item paid in cash with no invoice possible, for example a daily-wage labourer paid ₹2,000 for a one-time job. Users opt in per line item; vouchers auto-generate on approval, and an approver can generate or regenerate one from the request.

## Limit

Line items up to the **cash-voucher limit** qualify. Finance sets it in Settings → Programmes → Cash vouchers (`finance.manage`, or `settings.app_config`). It is stored in `app_config` under `cash_voucher_limit_paise` as whole paise; the default is ₹1,000 and the allowed range ₹1 to ₹10,000. ₹10,000 is a hard cap: cash paid to one person in a day above it doesn't count as spending on the trust's objects. `packages/shared/src/cash-voucher.ts` holds the key, default, cap, `parseCashVoucherLimit` (falls back to the default for a missing or invalid row, so a bad value can never lift the limit past the cap) and `qualifiesForCashVoucher(amountPaise, limitPaise)`.

How the limit reaches each side:

- **Writes**: `appConfig.upsert` lets `finance.manage` write the key and refuses any value outside ₹1 to ₹10,000 (`assertValidAppConfigValue`). The change is audited through the Zero mutation boundary like other `app_config` writes.
- **Zero mutators** (`packages/zero/src/mutators/reimbursement.ts`): `readCashVoucherLimit(tx)` reads the `app_config` row. On the server that is the database, so the server decides; on the client it is the synced row (`app_config` syncs to every non-external user), with the default until it arrives. `generateVoucher` refuses an item over the limit ("Vouchers can only be generated for items ≤ ₹2,000"); `approve` queues vouchers only for opted-in items within it; `create` and `update` keep an opt-in only for items within it and silently drop it otherwise (a box ticked before the amount grew).
- **Job**: `generate-cash-voucher` reads the row again and skips an item over the limit (`amount_exceeds_threshold`).
- **UI**: `useCashVoucherLimit()` (`apps/web/src/hooks/use-cash-voucher-limit.ts`) drives the line-items editor's checkbox and tooltip and the request detail's Voucher column.

Lowering the limit never touches vouchers already generated: they stay linked and downloadable. It applies to new generation requests and new submissions; the detail page hides Regenerate and shows "Over the ₹… voucher limit" for an opted-in item that no longer qualifies.

## Payee and acknowledgement

Ticking "Generate cash voucher" shows **Paid to** (`reimbursement_line_item.payee_name`, at most 120 characters) and an optional **Payee's mobile** (`payee_phone`, E.164 Indian mobile: `+91` and ten digits starting 6–9, `isIndianMobile`). Both columns arrive in migration `0142_voucher_payee`, sync through Zero to whoever can see the reimbursement, and are kept only on items that opt in. The name is required on a voucher item and must be in English letters: Latin letters including IAST ones (ṭ ḍ ṇ ṣ ṛ), digits, spaces and . ' - & / , ( ), checked and stored in NFC (`isLatinName`), because the voucher fonts can't print other scripts yet. The form checks the payee only on items that will get a voucher (ticked and within the limit, `addVoucherPayeeIssues` with the limit passed into the request schema). Hidden fields keep their values, so clearing and retyping an amount brings the payee back, but `toLineItemsPayload` sends the tick and payee only for ticked, eligible items. The mutator checks the same (`normalizeVoucherFields` in `packages/zero/src/mutators/voucher-fields.ts`). If the limit changes between the form loading and the save, the server drops an opt-in that no longer qualifies rather than refusing the save; that race is the only case where an opt-in disappears silently.

When the claimant was the one paid, a second box under the voucher tick, **Paid to me** on your own claim or **Paid to <name> (the claimant)** when filing for or editing someone else's, hides the payee fields. There is no column for it: a ticked box stores `payee_name` and `payee_phone` as NULL, and the voucher's fallback prints the claimant, so after "Change claimant" the payee follows the new claimant. The payload carries `payeeIsClaimant` explicitly, so a missing name is a choice rather than a forgotten field: the form skips the payee checks and `toLineItemsPayload` sends no payee for such an item, and `normalizeVoucherFields` stores nulls when it is true and still requires the name when it is false or absent. The edit form ticks the box for a voucher item with no stored payee (`mapLineItemsToFormValues`), which also covers items from before the payee fields. New voucher items start unticked, since the payee is usually someone else, such as a labourer or driver. The request detail shows such an item as "Paid to <claimant> (claimant)".

The voucher prints the payee's name and mobile under "Paid to" and the claimant in the details table as "Claimed by". With no payee stored (paid to the claimant, or an item from before the payee fields), "Paid to" prints the claimant's name, as the old voucher did, and the mobile on their profile (`user.phone`) when it is an Indian mobile (`voucherPayee` in `packages/jobs/src/handlers/voucher-render-check.ts`). The claimant's name is printed as stored, without the English-letters rule. The mobile is read when the voucher renders; changing it on the profile later doesn't regenerate the voucher. Beside the treasurer's signature is a **Received by** box: the payee's drawn signature with their name and when they signed (see "Payee signature"), or, without one, an empty box for "Signature or thumb impression of the payee", with a date line.

### Payee signature

The payee can sign on the volunteer's phone instead of on paper. On a cash-voucher item with a named payee (ticked, within the limit), the request detail shows **Collect payee signature** under the item's description to the claimant, finance (`finance.manage`) and approvers (`requests.approve`) while the request is pending or rejected. It opens a full-screen sheet on phones (`Sheet` from `responsive-sheet`), also on a touch screen under 540px tall (a phone on its side, where the statement and Confirm sit left of a pad sized by the height and the description is hidden), and a dialog on wider screens (`collect-payee-signature-dialog.tsx`). What the dialog shows (statement, the facts behind it, the signature it replaces) is frozen when it opens. Above the pad is the statement, in large type:

> I, {payee}, received ₹{amount} from Proud Indian for {purpose} on {date}.

`payeeSignatureStatement` in `packages/shared/src/payee-signature.ts` builds it: the amount in whole rupees (paise when there are any), the description (else the category) without a trailing full stop, and the expense date as a calendar day in India. The pad (`components/shared/signature-pad.tsx`) is a pointer-events canvas for finger, pen or mouse: white, with an X, a baseline, the payee's name and date under it and the hint "Sign or write your name with your finger"; dark ink, no pressure, one pointer at a time. It keeps a 2:1 shape and holds strokes as data (fractions of the pad, `lib/signature-ink.ts`), above the sheet/dialog switch, so a resize or a rotation across the phone breakpoint redraws them rather than losing them. While drawing, the page doesn't scroll (`touch-action: none`) and the drawer doesn't take the stroke as a swipe (`data-base-ui-swipe-ignore`). Undo removes the last stroke and Clear empties the pad. The canvas is labelled "Signature pad for {payee}" and described by the hint and the line under it: "If the payee can't sign here, print the voucher for a signature or thumb impression." The button reads "Waiting for signature" and stays disabled until the strokes run at least half the pad's width and span 15% of it (`hasEnoughInk`); under it sits "By signing, the payee confirms they received this amount." There is no geolocation.

Confirming crops the strokes to a PNG on white (`signaturePngBlob`; at most 1200 × 600, the whole pad), uploads it through the usual request upload (`getRequestUploadUrl`) and calls `reimbursement.collectPayeeSignature`, which:

- allows the claimant, `finance.manage` or `requests.approve`, refuses a voided request, and refuses an approved one ("The payee signature is locked once the request is approved");
- needs a voucher item within the limit, and refuses an item paid to the claimant ("Paid to the claimant, so no payee signature is needed"; the detail page says "No payee signature needed: the claimant was paid" instead of offering the action);
- locks the request row (`SELECT … FOR UPDATE`) and re-checks its status and void, so an approval can't slip in before the commit;
- compares the facts the client signed against (amount, category, description, expense day, payee name) with the item and refuses any difference, so a signature never records facts an edit has since changed; the server then words the stored statement itself;
- refuses a re-collect racing another (`replacesAttachmentId`, as with signed copies);
- claims the PNG into `attachments/reimbursements/<id>/` as `image/png`. The claim (`contentCheck: "payeeSignature"` in `apps/web/src/lib/r2-upload-claim.ts`) reads the file in chunks, stopping past its stated size or the cap, before copying it, applies the same checks to a durable target that already exists (the same temporary key may have been claimed before as an ordinary attachment), and refuses anything over 512 KB or whose PNG header isn't what the pad draws: 8-bit RGB or RGBA, non-interlaced, at most 1200 × 600 and at least 16 px a side with a 64 px longest side (`payeeSignatureImageProblem`). A small PNG can declare an image that takes gigabytes to inflate, and jobs run in the web process. inserts a `reimbursement_attachment` (`payee-signature.png`, type `file`; there is no separate attachment type), and sets the item's `payee_signature_attachment_id`, `payee_signature_statement`, `payee_signature_captured_at` (server time) and `payee_signature_captured_by` (migration `0147_payee_signature`);
- refuses a durable key another attachment row already holds;
- writes a history note ("Payee signature collected from …") whose metadata keeps the attachment, line item and statement, so the statement outlives a later edit.

The audit ledger records the attachment, line item, request and replaced attachment by ID only; the statement and object key are left out. The file is private like any request attachment: read through `/api/attachments/download`. Afterwards the item shows a "Signed by {payee} · {time}" chip with a thumbnail, and Re-collect until approval; approvers see the chip on the request before approving. A re-collected signature's earlier file stays among the attachments. Once approved, the signature is locked and is part of the approved record. Without one, the item says the payee signs the printed voucher, and the signed-copy upload below remains the paper fallback.

### Signed copy

Once a voucher exists on an approved request, the Voucher column offers **Upload signed copy** (then **Replace signed copy**) to the claimant who owns the request, finance (`finance.manage`) and approvers (`requests.approve`), without reopening the claim. The file goes through the usual request upload (`getRequestUploadUrl`, a temporary R2 key under the uploader's own prefix) and `reimbursement.attachSignedVoucher` claims it into `attachments/reimbursements/<id>/`, inserts a `reimbursement_attachment` row, points `signed_voucher_attachment_id` at it and writes a history note. The client sends the signed copy it saw (`replacesAttachmentId`), and a mismatch is refused, so two uploads can't race. A replaced copy is not deleted: it stays among the request's attachments as evidence. The audit ledger records the line item, the new attachment and the replaced attachment by ID only.

### Edits keep links

`reimbursement.update` deletes and re-inserts the line items; `planVoucherFields` decides what survives. A voucher survives an edit when everything it prints is unchanged — amount, description, category, the request's expense date (compared as a calendar day in India, so re-picking the same day changes nothing), and the payee name and mobile when the item is still a ticked, eligible voucher item (an item paid to the claimant compares as no name and no mobile, so ticking or unticking that box regenerates the voucher) — and its file is still attached under the same id with the same object key (the signed copy is checked the same way). Then the stored opt-in and payee are kept as they are, even if the limit was lowered since (an explicit untick on an eligible item is stored, and the voucher stays linked as evidence), and the links are put back after the attachments are re-inserted. Otherwise the voucher is stale: the links are dropped (the old files stay among the attachments) and the item is treated like a new one. On an approved request, an admin's edit queues a voucher for every opted-in item within the limit that is new, changed or still has none, as approval would. Regenerating a voucher unlinks the signed copy, because it was signed against the old number.

The payee signature follows the same stale rule on its own, whether or not a voucher exists yet: it survives an edit only when the amount, description, category, expense day, payee name and mobile are unchanged, the item is still a ticked, eligible voucher item naming that payee, and its PNG is still attached under the same id and key. An item the lowered limit put out of reach can't show the voucher box, so its stored opt-in, payee and signature stand, as for the voucher. `reimbursement.update` takes the same row lock before reading the items, so a signature collected meanwhile isn't wiped when they are replaced. The linked PNG can't be removed by an edit: when the edit form leaves it out, the mutator keeps the attachment row and its R2 object. Otherwise the four signature columns are cleared (the PNG stays among the attachments as evidence) and the history says "Payee signature cleared: the item changed after it was signed". A voucher already rendered with that signature is stale too, so an approved request queues a fresh one without it. Regenerating a voucher or changing the claimant keeps the signature, since the statement names neither the voucher number nor the claimant.

Changing the claimant (`reimbursement.changeClaimant`, see "Claim for others" in `finance-and-programmes.md`) unlinks every voucher and signed copy on the request and, when approved, queues fresh vouchers naming the new claimant; a render whose claimant changed meanwhile is discarded.

## Generation

**Async job**: pg-boss `generate-cash-voucher` (payload: `{ approverUserId, lineItemId, reimbursementId }`).

1. Loads the line item, checks the limit and that the reimbursement is approved.
2. Allocates `CV-<year>-<seq>` from `voucher_seq`.
3. Reads the payee's signature PNG from R2 when the item links one, before drawing a number (`readPayeeSignatureImage`): the size before downloading and the PNG header before decoding, with the same rules as the claim. A missing row or object (`payee_signature_missing`), a file over the limits (`payee_signature_too_large`) or in another format (`payee_signature_invalid`) prints the empty box and is logged; other storage errors throw so the job retries. Then `packages/pdf/src/cash-voucher.tsx` renders the PDF with it in the Received by box (see `pdf.md`).
4. Uploads to R2, then in one transaction inserts the attachment, points `voucher_attachment_id` at it, clears `signed_voucher_attachment_id` and deletes the previous voucher's row; the old R2 object is removed best-effort.
5. The queue's policy is `stately` with `singletonKey: voucher-<lineItemId>`: one queued and one running job per line item, so repeated requests collapse and an edit made while a voucher renders queues one more. pg-boss can't change an existing queue's policy, so a deployment whose queue predates this keeps the `standard` policy until the queue is recreated; the commit check below keeps duplicate jobs harmless there, though each duplicate still draws a number from `voucher_seq`, so such deployments can show gaps in voucher numbers.
6. The commit locks the line item and links the new PDF only if the item and its request still hold what was rendered (amount, description, category, payee, payee signature, expense date). If an edit changed them meanwhile, the PDF is discarded and the newer job wins. When only the signature changed, nothing queued a newer job, so the job queues itself again.

**Config**: `VOUCHER_ORG_*` env vars (name, address, phone, email, registration) and `VOUCHER_FINANCE_ADMIN_NAME` (the approver printed beside the treasurer signature, `packages/pdf/assets/signature.png`).

A voided reimbursement (finance Option B, `finance-and-programmes.md`) keeps its vouchers and signed copies; their numbers stay used, since `voucher_seq` never hands one out twice. The detail page marks each one VOID and offers no regenerate or signed-copy upload, and `generate-cash-voucher` makes no voucher for a voided request.
